## Problem Statement

같은 사람을 노리고 같은 개념(verify gate, Human Gate, Codex review, apply boundary)을 다루는 두 alpha 제품(NEKOWORK 0.1.0-alpha.10, NEKOFORGE 0.5.0-alpha.0)이 별도 레포 + 0% 코드 공유 상태로 운영 중. 외부 demand가 0인 지금이 메이저 구조 재편의 마지막 기회. "별도 운영 vs 통합"을 결정한다.

## Demand Evidence

- 두 제품 모두 일일 의존 사용자 없음. NEKOFORGE의 명시된 베타 진입 조건(외부 사용자 1명이 PR에 실행해 REPORT.md + decision.json + quality-score.json 제출)도 미달.
- GitHub star / npm 다운로드 수준은 있으나 "사라지면 일이 막힐" 의존은 두 제품 모두 없음 (Q1 답변).
- 결론: pre-demand alpha. 재구조화의 deadline 압박 없음. 외부 사용자 attach 후 비용은 10배.

## Status Quo

NEKO* 없는 세상에서 개발자들은 AI 에이전트가 만든 변경을 "그냥 Claude/Codex/Cursor 자체 review + 테스트 통과만 확인"하는 디폴트로 살고 있음 (Q2). 진짜 검증 레이어 없음. 갭은 존재하지만 마찰이 가벼워서 사람들은 한 번 크게 데이기 전까지 도입 동기가 약함.

## Target User & Narrowest Wedge

**Same person across both products** (Q3): NEKOFORGE는 NEKOWORK의 superset. 사용자 인지에서 두 제품은 한 제품의 두 깊이.

**Narrowest wedge** (Q4): "Claude Code·Cursor·Codex가 돌린 PR을 적용전에 30초 게이트하는 단일 CLI". NEKOFORGE의 14단계·worker factory·rule pack 13종은 wedge가 아니라 확장.

## Constraints

- Tech stack 고정: NEKOFORGE = TypeScript + Node.js ≥20, NEKOWORK = Node.js
- 외부 사용자 0 시간 창 한정 (P3)
- 두 레포 모두 npm publish + GitHub Actions CI 가동 중
- NEKOWORK npm 좌표(@ps-neko/nekowork)는 이미 wedge에 align됨

## Premises

P1 — ICP integration: 같은 desperate ideal user, NEKOFORGE = NEKOWORK superset
P2 — Wedge anchored: "30초 게이트 CLI"가 진입 wedge
P3 — Time window: 외부 demand 0인 지금이 메이저 재구조화의 마지막 기회
P4 (revised) — 미래 중요성(자율 에이전트 시대 oversight 게이트)은 그럴듯하나 검증되지 않음. 진짜 시장 테스트는 "외부 사용자 5명이 wedge를 시도해보고 워크플로우 도입 의사 표현"
P5 — 현 구조(별도 + 0% 공유 + 같은 ICP)는 worst-of-both-worlds. 유지비 2배 + drift 위험 + 한 사용자에게 두 README 강요

## Cross-Model Perspective (Codex cold read)

**Steelman**: "자율 코딩 에이전트를 위한 trust boundary. 로컬·빠르고·증거 생성하는 게이트로, AI가 만든 코드 변경이 diff 통제권을 사람이 잃기 전에 적용 안전한지 판단. 가장 강한 제품은 'AI code review'가 아니라 deterministic readiness contract: agent proposes, NEKO verifies, human decides."

**가장 드러난 답변**: Q4 — wedge 답변이 product 자체. 모든 것은 확장/아키텍처/research surface.

**Premise challenge**: P4의 future-fit이 plausible은 하나 validated는 아니라고 지적. 숨은 가정은 "사용자가 독립 게이트를 도입할 것" — 실제로는 agent-native checks, CI, IDE-integrated review, 또는 platform-native policy layer를 선호할 수도 있음. 진짜 검증 = 사용자 5명이 실제 PR에 시도해보고 "유용하지만 워크플로우에 추가하진 않겠다" 또는 "Claude Code/Cursor/GitHub에 번들될 때만 쓰겠다" 같은 반응이 나오는지. **이 challenge는 채택되어 P4 수정에 반영**.

**Prototype 제안**: NEKOWORK = 공개 제품, NEKOFORGE = 내부 엔진/advanced mode. 단일 monorepo at Ps-Neko/NEKOWORK. packages/nekowork-cli + packages/quality-core + packages/forge-engine. 14-stage 어휘는 `--profile forge` 옵션에만 노출. 첫 외부 산출물 = @ps-neko/nekowork@0.2.0-alpha.0, headline "30-second gate for AI-generated PRs before apply".

## Approaches Considered

### Approach A: Soft Funnel (narrative + dependency only)
Summary: 두 레포 유지, README 재작성으로 입구/깊은 모드 framing, NEKOFORGE가 @ps-neko/nekowork dep 추가
Effort: S (human 1-2일 / CC 1-2시간), Risk: Low, Coverage: 4/10
Pros: 가장 빠른 ship, 롤백 쉬움, 두 레포의 history/star/CI 그대로
Cons: drift 문제 미해결, 유지비 2배 유지, 한 사용자에게 두 README 강요 그대로

### Approach B: Monorepo Merge (chosen)
Summary: 단일 monorepo at Ps-Neko/NEKOWORK. 3개 패키지(nekowork-cli + quality-core + forge-engine). NEKOFORGE 레포 archive. @ps-neko/nekowork@0.2.0-alpha.0 출시
Effort: L (human 1-2주 / CC 1-2일), Risk: Medium, Coverage: 10/10
Pros: 사용자 인지 단일화, drift 0, 단일 npm 좌표, P3 시간 창 활용, Codex·Claude 양쪽 추천
Cons: 마이그레이션 작업 큼, NEKOFORGE history가 archive로 떨어짐, monorepo 도구 체인(turbo/nx/changesets) 도입 필요

### Approach C: Sleeper SDK (private internal)
Summary: NEKOFORGE 레포 maintenance-mode + npm publish private화, NEKOWORK이 internal API 소비
Effort: M (human 3-5일 / CC 4-6시간), Risk: Low-Medium, Coverage: 7/10
Pros: NEKOFORGE history/star 보존, 이후 B로 확장 가능, 공개 얼굴 단일화 효과는 B와 유사
Cons: private npm 셋업 작업, "왜 NEKOFORGE 레포는 살아있나" 외부 혼란 가능, 결국 B로 가야 할 가능성 큼

**P3 self-rejection note**: C는 "이후 B로 확장 가능"을 옵션 가치로 내세우지만 P3가 명시한 "지금이 마지막 기회"는 deferred 비용이 즉시 비용보다 큼을 함의. P3를 유지하면 C는 자동 기각. P3를 "현재가 가장 저렴하나 6주 후도 가능"으로 약화시키면 C가 살아남음. 본 문서에서는 P3를 약화시키지 않으므로 C는 후보에서 제외.

## Recommended Approach

**Approach B: Monorepo Merge.**

이유:
1. **P3 시간 창**: 외부 사용자 0인 지금이 L-effort 작업의 유일하게 합리적인 시점. 사용자 5명이 붙은 후 동일 작업은 10배 비용 + breaking change risk.
2. **P1·P2 정렬**: "같은 사람의 두 깊이"는 외부에 명시적 단일 product로 보내야 인지된다. Soft Funnel(A)은 narrative만 바꿔 사용자에게 "여전히 두 곳이네"를 시그널.
3. **Cross-model 합의**: Claude·Codex 둘 다 같은 방향. Codex는 더 강한 commit (3-package monorepo 구체).
4. **wedge 강제**: 14-stage 어휘가 landing path에서 사라지면 wedge가 자연스럽게 first impression이 됨.

C(Sleeper SDK)는 B로 가는 deferred 형태. P3가 명시한 시간 창을 고려하면 deferred 비용이 즉시 비용보다 큼.

## Distribution & Release Mechanics

- **공개 npm 좌표**: `@ps-neko/nekowork@0.2.0-alpha.0` (첫 monorepo 출시). 0.5.0 → 0.2.0 다운그레이드 우려는 README/CHANGELOG에 "새 좌표는 새 history. NEKOFORGE 0.5.0-alpha 사용자(추정 0명)에게는 마이그레이션 가이드 + npm deprecate 안내" 명시.
- **NEKOFORGE deprecation**: `npm deprecate "@ps-neko/nekoforge@*" "moved to @ps-neko/nekowork — see https://github.com/Ps-Neko/NEKOWORK"` 실행. (현재 NEKOFORGE가 npm publish 중인 경우만; private면 skip)
- **내부 패키지**: workspace-only. 명명은 스코프 없는 `quality-core`, `forge-engine` 또는 `@ps-neko/quality-core`+`"private": true`로 npm registry 노출 차단. 권장: 후자 (`@ps-neko/` 스코프 유지하되 publish 차단 — name collision 방지).
- **GitHub repo**: `Ps-Neko/NEKOWORK`이 single source. `Ps-Neko/NEKOFORGE`는 archive + README "→ moved to NEKOWORK" pointer + issue tracker도 read-only로 전환됨에 따라 핵심 open issue는 NEKOWORK으로 미리 transfer.
- **Git history 보존**: NEKOFORGE 0.5.0-alpha까지의 커밋 히스토리를 `git filter-repo --subdirectory-filter` 또는 `git subtree add`로 monorepo의 `packages/forge-engine/` 하위로 이관. 단순 archive 시 14-stage 변천사 추적 불가 — 이걸 inventory 단계 산출물에 포함.
- **Monorepo 도구 결정 (decided here, not deferred)**: **pnpm workspaces + Changesets**. NEKOWORK/NEKOFORGE 모두 npm을 사용 중이라 lockfile 재생성·CI runner pnpm setup·publish 워크플로우 전환 비용은 inventory 단계에서 정량화. 대안(Turbo/Nx)은 over-engineering으로 기각.
- **CI/CD**: 기존 NEKOWORK GitHub Actions(harness-validate)는 monorepo 전제 가정 안 함 — `working-directory`, cache key, artifact path 모두 재작성 필요 (0.5-1일). forge-engine 패키지 test/lint도 같은 워크플로우의 build matrix로 추가.
- **릴리스 메커니즘**: Changesets로 nekowork-cli만 publish. quality-core/forge-engine은 `"private": true` 유지 (workspace internal). GitHub Releases v0.2.0-alpha.0 태그 + CHANGELOG 자동 생성.
- **30-second performance gate**: README headline "30-second gate"의 정확성 보장을 위해 CI에 성능 회귀 테스트 추가 (fixture PR 1개에 대한 nekowork check 실행시간 < 30s assertion).

## Decisions made in this doc (no longer open)

1. **Monorepo 도구**: pnpm workspaces + Changesets.
2. **NEKOFORGE archive 시점**: alpha.0 ship과 **동시에** (pointer 명확).
3. **forge 진입점**: `nekowork check --profile forge` 플래그 (subcommand 분리 시 wedge가 두 입구를 가지게 됨 → wedge 약화). `nekowork forge` 별도 subcommand는 미도입.
4. **forge-engine API surface**: quality-core가 인터페이스(verdict, evidence, score schema)를 정의하고 forge-engine이 구현. quality-core → forge-engine 단방향 의존만 허용. 순환 발견 시 inventory 단계에서 인터페이스를 quality-core로 끌어올림.

## Open Questions (실제 미결)

1. **quality-core 추출 기준 inventory**: NEKOFORGE의 어떤 모듈이 quality-core 인터페이스로, 어떤 게 forge-engine 구현으로 가는지 day-1 산출물로 작성 필요. 산출물 schema: `모듈명 / 원적 레포 / 새 위치 / 의존 / 충돌`.
2. **현재 NEKOFORGE 외부 컨트리뷰터의 진행 중 PR 처리**: archive 전 미해결 PR 인벤토리 (있다면).
3. **5-user wedge test의 reaction 수집 메커니즘**: GitHub issue template? Google Form? DM 텍스트? The Assignment 실행 전 결정 필요.
4. **REPORT.md / decision.json / quality-score.json 산출물 규약 ownership**: quality-core(인터페이스) vs forge-engine(구현) 어느 쪽에 schema/writer가 살지 — inventory 단계에서 확정.
5. **Rule Pack 13종 / Skill Pack 13종 location**: forge-engine 내부로 두되 미래에 `@ps-neko/nekowork-pack-*` 형태로 외부 plug-in publish 가능성 — 본 monorepo merge 범위 외이나 forge-engine 디렉토리 구조에서 미리 분리 (`packages/forge-engine/packs/{rule,skill}/`).

## Success Criteria

**Phase 1 — ship (1-2주 안)**
- @ps-neko/nekowork@0.2.0-alpha.0 npm 출시 + README "30-second gate" headline + 성능 회귀 테스트 green
- forge-engine 내부 모듈은 nekowork-cli 빌드와 같은 CI에서 green
- NEKOFORGE 레포 archive 완료 + pointer + git history는 forge-engine subdirectory에 보존
- npm `@ps-neko/nekoforge` (publish된 경우) deprecate 처리 완료

**Phase 2 — validate (ship 후 4주 안, 총 6주 시계)**
- 외부 사용자 5명이 wedge를 실제 PR에 적용한 후 명시적 피드백 (P4 revised의 진짜 검증 테스트)
- 측정 기준 (명시적):
  - **P4 confirm**: ≥3/5명이 "워크플로우에 추가하겠다" OR "다른 사람에게 추천하겠다"고 명시
  - **P4 reject (a)**: ≥3/5명이 "유용하지만 standalone CLI는 워크플로우 추가 안 함"
  - **P4 reject (b)**: ≥3/5명이 "Claude Code skill / Cursor extension / GitHub Action 형태였다면 도입"
  - reject(a)와 (b)는 다른 의미 — (a)는 wedge 자체가 약한 신호, (b)는 distribution shape이 잘못된 신호
- P4 reject 시 행동: 독립 CLI를 유지하지 않고 (b)면 가장 많이 언급된 distribution shape으로 pivot, (a)면 wedge 자체를 다시 좁히는 새 office-hours 세션

**Ship 전 P4 미검증 상태 정당화**: monorepo merge는 P4 reject 시에도 후회 없는 결정인가? — YES. 이유: ① P5 (worst-of-both-worlds 현 구조)는 P4와 독립적으로 참. ② P4 reject 시 pivot 방향(Claude Code skill 등)이 어느 쪽이든 internal package(quality-core, forge-engine)는 재사용. 별도 레포 + 0% 공유 상태는 어느 pivot에도 부담. 즉 monorepo는 P4 검증과 독립적인 hygiene 결정이고, 동시에 P4 검증의 ship 비용을 낮춤 (1개 npm publish vs 2개).

## The Assignment

**한 가지 구체적 실세계 액션** (코딩 아님):

> **6주 내에 5명의 외부 개발자(Claude Code·Cursor·Codex를 실제 업무에 쓰는 사람)에게 "당신이 최근에 AI 에이전트가 만든 PR 하나에 nekowork check를 30초 돌려보고 reaction을 알려줄 수 있냐"고 직접 메시지 또는 코드 리뷰 요청을 보낸다. 채널은 Twitter/X DM, Discord, 한국 OSS Slack, 직장 동료 어느 곳이든. 5명의 이름과 채널을 리스트로 적어두고 보낸 날짜를 기록한다.**
